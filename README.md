# KAMP 자원 최적화: 15분 수요전력 day-ahead 예측 파이프라인

원본 CSV에서 정제, 15분 단위 피처, 교차검증, 최종 테스트, 결과물 생성까지 명령 하나로 실행한다.

## 실행

```bash
pip install -r requirements.txt
# data/okm_augumented_2021.csv 위치에 원본을 둔다(경로는 --data로 변경 가능)
python run.py              # 전체 실행
python run.py --fast       # ablation·누수 시연 생략(반복 실험용)
python run.py --skip-lstm  # LSTM 생략(torch가 없으면 자동 생략)
python tests/test_sequences.py   # LSTM 입력 창 정렬 검증
```

분석 노트북은 `run.py` 실행 후에 연다.

```bash
pip install jupyter                      # 선택: shap도 설치하면 02 노트북에 SHAP 그림이 추가됨
jupyter notebook notebooks/
# 명령줄에서 실행 결과까지 저장하려면
jupyter nbconvert --to notebook --execute notebooks/01_data_diagnosis.ipynb --output-dir outputs/notebooks
jupyter nbconvert --to notebook --execute notebooks/02_results_analysis.ipynb --output-dir outputs/notebooks
```

CPU 1코어 기준 전체 약 6~7분, `--fast` 약 4분. LightGBM을 설치하면 자동으로 GBM 백엔드로 쓰이고 더 빨라진다.
정제는 전부 코드로 수행하며 원본 파일은 수정하지 않는다.

## 변수 해석 (해석 A)

`15분`, `30분`, `45분`, `60분`은 각각 hh:00~15, 15~30, 30~45, 45~정각 구간의 **15분 평균수요전력(kW)** 으로 본다.
따라서 `평균`(시간 평균 kW)은 숫자상 그 시간의 사용량(kWh)과 같고, 월간 최대수요전력은 15분 값들의 월 최댓값이다.
가이드북은 각 값을 "최대수요전력"이라 부르지만, 한전 기준 최대수요전력은 요금 기간당 하나의 값이므로
현장 장치명을 따른 느슨한 명칭으로 해석했다.

## 과제 정의와 가정

- **Day-ahead**: D일 00:00 시점에 D-1일까지의 실측 전력으로 D일 96개 15분 슬롯을 예측한다.
- **기본값은 예측 시점에 확실히 알 수 있는 정보만 쓴다**: 달력(시간, 요일, 공휴일, 교대 구조)과 과거 전력.
- 아래 정보는 미래에 확정되지 않으므로 기본적으로 끄고, ablation에서 켰을 때의 효과만 보고한다.
  - `PRODUCTION_PLAN`: 생산계획(`hourly` 시간별 / `daily` 일 총량 / `none`)
  - `USE_WEATHER`: 기상(실측을 예보 대용으로 쓰는 가정)
  - `USE_PLANNED_SHUTDOWN`: 계획 휴무 달력(`PLANNED_SHUTDOWNS`). 실제 공장의 휴무 계획을 미리 안다면 켤 수 있다.
    데이터를 보고 전력이 낮은 날을 골라 채우면 누수다. (공휴일은 달력으로 확정되므로 항상 `is_holiday`로 사용)
- **월 피처는 기본적으로 쓰지 않는다**(`USE_MONTH=False`). 학습 기간 8월 평일의 절반이 휴가 주간이라 월 피처가 휴가를
  "8월의 특성"으로 학습했고, 빼면 CV MAE가 gbm 33.4→27.1, gbm_1d 25.8→21.5로 개선됐다(CV 기준으로 결정). 트리·LSTM에 함께 적용된다.
- **시간 표기는 구간 시작 기준**이다. `15분` 컬럼(00:00~00:15)은 00:00, 하루는 00:00~23:45의 96칸이다.
  구간 끝 기준(00:15~24:00)으로 만든 데이터를 쓰면 하루의 마지막 칸이 다음 날로 분류되어 요일·공휴일 표시가 한 칸씩 어긋나므로,
  다른 데이터와 비교할 때는 15분을 당겨 맞춘다. `tests/test_sequences.py`가 하루 경계와 요일·공휴일의 일관성을 검사한다.

## 입력 과거 범위 비교 (1d vs 7d)

학습 데이터 범위(예측일 이전 전체, 확장 윈도우)는 모든 모델이 같고, **예측할 때 입력으로 보는 과거 범위**만 두 가지로 나눠 비교한다.

| 모델 계열 | 1d (전날만) | 7d (지난주까지) |
|---|---|---|
| 기준 모델 | `naive_yesterday` (어제 같은 칸) | `naive_lastweek` (지난주 같은 칸) |
| GBM | `gbm_1d` (lag_1d, 전날 평균·최대·마지막) | `gbm` (여기에 lag_7d, 지난주 평균 추가) |
| LSTM | `lstm_1d` (인코더 입력 96칸) | `lstm_7d` (인코더 입력 672칸) |

LSTM에 "이전 전체"를 한 시퀀스로 넣는 것은 날마다 길이가 달라지고(수천~2만 칸) 학습이 사실상 불가능하므로,
트리 모델이 쓰는 가장 긴 래그(7일)와 같은 범위로 맞췄다. 결과는 `results.md`의 "입력 과거 범위 비교" 표와 02 노트북 2-1절에 정리된다.

## LSTM 비교 모델

`src/lstm_model.py`는 첨부한 Seq2Seq LSTM 구조를 그대로 옮긴 것이고, 데이터 처리와 학습은 `src/seq.py`가 맡는다.
모델별 설정은 `config.LSTM_MODELS`, 학습 설정은 `config.LSTM_TRAIN`에 있다.

| 입력 | 내용 |
|---|---|
| 과거 입력(인코더) | 예측 시작 직전 window칸(1d: 96, 7d: 672)의 [전력(정전 대체값) + 그 시점의 달력·상태] |
| 미래 입력(디코더) | 예측할 96칸의 달력·상태(시간 sin/cos, 요일 one-hot, 공휴일·휴무·기동·점심 표시) + **같은 칸의 과거 전력**(lstm_1d: 1일 전, lstm_7d: 1일 전·7일 전) |
| 타깃 | 예측할 96칸 전력 |

- **디코더 래그**: LSTM_prediction.ipynb처럼 예측 칸마다 과거 전력을 직접 넣어 칸별 참조값을 준다. 과거 범위 정의를 지키도록
  lstm_1d는 1일 전 값만 받는다(트리 gbm_1d / gbm과 같은 구분). 타깃과 같은 기준으로 스케일한다. 인코더에는 래그를 넣지 않는다.
- **요일 one-hot**: 토(새벽만 가동)·일(대기)·월(재가동) 패턴이 서로 독립적이라 sin/cos 대신 one-hot을 쓴다.
- **학습 설정(노트북과 동일)**: L1 손실, AdamW(lr 2e-4, weight decay 1e-5), ReduceLROnPlateau(0.5배, patience 10),
  batch 64, 최대 150 epoch, 조기 종료 patience 20, 기울기 클리핑 1.0, 최저 모니터 손실의 가중치 복원.
- **조기 종료 모니터**: 학습 구간 마지막 7일(채점하는 검증 주와 별개). 모니터 날짜와 같은 복제그룹이 타깃에 들어 있는 학습 샘플은
  뺀다(CV purge와 같은 규칙). 빼지 않으면 복제본을 외워 모니터 손실이 낮아지는 쪽으로 조기 종료가 왜곡된다(첫 폴드에서 166개 제외).
- **노트북(make_sequences)과 다른 점**: 배열을 미리 만들지 않고 시작 위치만 저장해 배치마다 잘라낸다. 학습 샘플은 `stride`칸(기본 4칸 = 1시간)
  간격으로 시작하고, 평가·예측은 항상 00:00 시작이다. 표준화 기준은 폴드마다 학습 행에서만 계산한다. 검증은 단일 분할 대신 주간 walk-forward다.
- **정렬 검증**: `python tests/test_sequences.py`. torch 없이 돌아가며, 학습하지 않고 특정 입력을 그대로 내보내는 가짜 모델로
  과거 창(lag_1d, lag_7d와 일치), 미래 입력, 디코더 래그, 모니터 복제그룹 제거, 시간 표기를 확인한다.
- **실행 시간**: torch가 없으면 자동으로 건너뛴다(`--skip-lstm`으로 수동 생략도 가능). 노트북 설정(batch 64, lr 2e-4, 최대 150 epoch)이라
  CPU에서는 오래 걸리고, 특히 `lstm_7d`가 느리다(폴드 7개 + 테스트 1번 = 8번 학습). GPU를 권장한다.
  GPU에서는 cuDNN LSTM 특성상 실행마다 아주 작은 차이가 날 수 있다.

## 검증 설계

연속된 원본 데이터는 7월 이후에만 있다. 4~6월을 검증에 쓰면 채점할 원본일이 거의 없고,
학습 데이터도 대부분 복제본이라 최종 운영 상황을 대표하지 못한다.
실제로 4~7월 월별 검증을 쓰면 "지난주 같은 시각" 나이브가 선정되지만, 여름휴가 주간이 있는 8월에는 가장 나쁜 모델이 된다.

- **모델 선정**: 2021-07-05부터 주 단위 walk-forward 7개 폴드. 매 폴드마다 그 이전 전체로 재학습하며, 휴가 주간과 대체공휴일이 포함된다. 선정 규칙은 점예측 모델 중 CV MAE(채점일 가중) 최소로 사전에 고정했다.
- **최종 테스트**: 2021-08-23 ~ 09-14(전부 원본). 선정과 튜닝에 쓰지 않는다.
- **누수 방지**: 검증일과 같은 복제그룹의 학습일을 제거하고, 피크 임계값은 학습 구간에서만 정한다.
- 누수 시연(`leakage_demo.csv`): 같은 GBM으로 랜덤 행·랜덤 일·랜덤 복제그룹 분할의 점수를 비교한다.

**정전 래그 대체의 경위.** 정전 다음 날(8/30) 경보가 거의 울리지 않은 원인을 테스트 구간 오류분석에서 찾아 고친 것이다.
테스트를 보고 내린 결정이므로 보고서에 경위를 밝힌다. 조정 가능한 상수 없이 규칙만 쓰며(`LAG_IMPUTE_OUTAGE`, `LAG_IMPUTE_WEEKS`),
CV 기간에는 정전이 없어 CV 점수에는 영향이 없다. 직전 값 유지(정전 직전 값이 이미 0)와 기간 평균(요일·시간 구조가 사라짐)은
비교 실험에서 더 나빠 채택하지 않았고, 정전 후 증산 보정은 학습 기간에 정전이 없어 검증할 수 없으므로 넣지 않았다.

## 하이퍼파라미터 탐색 (`tune.py`)

```bash
python tune.py --trials 60                 # Optuna가 있으면 TPE + 가지치기, 없으면 랜덤 탐색
python tune.py --trials 2 --seed-check 0 --max-trees 300   # 동작 확인용
```

- `run.py`와 같은 주간 CV 폴드·채점 기준(채점일 가중 MAE)만 쓰고 테스트는 보지 않는다. 0번 시도는 현재 config 값(비교 기준)이다.
- 트리 개수는 탐색하지 않고, `learning_rate=0.05`로 최대 2,000개를 한 번 학습한 뒤 체크포인트별 예측으로 7개 폴드 공통 최적값을 고른다.
- 추천값은 1-표준오차 규칙으로 고른다(최고 점수에서 표준오차 이내 후보 중 가장 단순한 것). 기준보다 나은 폴드 수와 시드별 재평가도 함께 보고한다.
- 결과: `outputs/tuning_trials.csv`(모든 시도), `outputs/tuning_summary.md`(추천값과 config.py에 붙일 코드).
- 추천값은 자동 반영하지 않는다. 대부분의 폴드에서 기준보다 나을 때만 `src/config.py`에 옮기고 `python run.py`를 다시 실행한다.
  하이퍼파라미터는 백엔드(LightGBM/sklearn)마다 다르므로, 최종 제출 환경과 같은 백엔드에서 탐색한다.

## 평가지표

- 회귀: MAE, RMSE, NMAE, 정전 제외 MAE, 시간 단위 MAE(= kWh 오차), 일 최대수요 오차, 피크 발생 시각 적중률(±1시간)
- 피크 이벤트: "15분 수요 ≥ 학습기간 90분위"를 이벤트로 정의하고 Precision, Recall, F1, FN(놓친 피크), FP(헛경보)를 계산한다.
  대회 평가표의 F1·FN·FP 요구를 회귀 과제에 맞게 옮긴 것이다.
